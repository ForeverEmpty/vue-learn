# Java 并发 01·02 复习：共享变量、竞态条件与 synchronized

## 1. `value++` 包含哪些逻辑步骤？请用两个线程都读取到 `10` 的交错过程说明为什么最终结果可能是 `11`，而不是 `12`。

读取value，值++，写回value
A 读取共享 value：10
B 读取共享 value：10
A 根据旧值计算：11
B 根据旧值计算：11
A 写回：value = 11
B 写回：value = 11

> **批改：正确。** `value++` 已准确拆成读取、计算和写回，交错过程也说明了两个线程都基于旧值 `10` 计算出 `11`。后一次写回覆盖前一次写回，因此丢失一次更新。

## 2. main 线程已经对所有 worker 调用了 `join()`，为什么仍然可能丢失更新？`join()` 与 `synchronized` 分别提供什么保证？

join()是保证调用者等待线程完成后再执行，但两个线程直接还是会存在竞争
synchronized保证方法仅一个线程占用

> **批改：基本正确。** `join()` 保证调用它的线程等待目标 worker 结束，却不限制多个 worker 之间如何交错执行。`synchronized` 的互斥范围需要说得更精确：同一时刻只能有一个线程持有同一把锁并进入受它保护的代码，而不是所有线程中的该方法全局只能执行一次。

## 3. `public synchronized void increment()` 锁住的是什么？两个线程共享同一个 `SharedCounter`，与分别使用两个 `SharedCounter` 时，互斥关系有什么区别？

### Codex 补充答案

实例同步方法锁住的是当前调用对象，也就是 `this` 对应的 `SharedCounter` 实例。

如果两个线程共享同一个 `SharedCounter`，它们调用 `increment()` 时竞争同一个对象的内置锁；一个线程进入方法后，另一个线程必须等待锁释放，因此两次加一不会交错。

如果两个线程分别使用不同的 `SharedCounter`，每个对象都有自己的内置锁。两个线程获得的是不同的锁，所以它们可以同时执行各自对象的 `increment()`，彼此不形成互斥。

> **批改：本题由 Codex 应要求补充。** 核心关系是“实例同步方法锁住 `this`；是否互斥取决于是否使用同一个对象，而不是方法名是否相同”。

## 4. 第二章为什么既测试最终计数，又检查 `increment` 是否声明为 `synchronized`？只依靠一次多线程运行结果有什么问题？

### Codex 补充答案

最终计数测试检查外部行为：所有线程结束后，每一次加一是否都被保留下来。`synchronized` 修饰符检查则确认本章要求的实现机制：`increment()` 是否确实使用对象内置锁保护临界区。

线程调度具有不确定性。没有同步保护的错误实现通常会丢失更新，但某一次运行也可能恰好没有形成会丢失更新的交错，从而偶然得到正确计数。只依赖一次运行结果会产生误判。因此本章同时检查行为结果和同步声明，使测试不依赖一次随机调度是否暴露问题。

> **批改：本题由 Codex 应要求补充。** 在一般项目中测试通常更关注可观察行为；本章额外检查修饰符，是为了明确练习目标并避免错误实现因偶然调度通过测试。
