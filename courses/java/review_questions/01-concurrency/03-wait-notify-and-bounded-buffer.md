## 1. 消费者在空缓冲区中调用 `take()` 后，会怎样经历检查条件、`wait()`、生产者放入元素、`notifyAll()`、重新竞争锁和再次检查条件？请按顺序描述。

先检查缓冲区是否有资源，如果没有则循环等待wait()，直到生产者放入资源，通知所有等待资源的消费者，得到资源的消费者对资源进行上锁消费，未得到资源的消费者继续等待，直到再次有资源

消费者进入同步 take() 时先获得缓冲区锁，未获得资源进入等待集并释放锁

> **批改：主线基本正确，但“得到资源后上锁”这一顺序需要修正。** 消费者调用同步 `take()` 时先获得的是缓冲区 `this` 的锁；发现为空后，`wait()` 释放锁并进入该对象的等待集。生产者获得同一把锁、放入元素并调用 `notifyAll()`，但要等生产者退出同步方法后才释放锁。被唤醒的消费者先重新竞争并获得锁，`wait()` 才返回，然后由 `while` 再次检查非空条件；条件满足后才移除元素。线程竞争的是对象锁，不是直接竞争某个资源。

### 修正复核

已修正为消费者先获得缓冲区锁，发现条件不满足后由 `wait()` 释放锁并进入等待集。结合原答案中的生产、通知和再次等待过程，本题通过。完整顺序是：获得锁 → 检查为空 → `wait` 释放锁 → 生产者获得锁并放入 → `notifyAll` → 生产者释放锁 → 消费者重新获得锁 → `while` 复查 → 取出元素。

## 2. 为什么生产者在缓冲区已满时不能持有锁循环检查，也不能用 `Thread.sleep()` 代替 `wait()`？

生产者在缓冲区满后，无法再放入资源，此时持有锁就会导致消费者无法消费，生产者也无法再放入资源导致死锁
使用Thread.sleep()并不能释放锁，而且需要编写程序时预估时长

> **批改：正确。** 持锁忙等和在同步方法中 `sleep()` 都不会释放缓冲区锁，消费者无法进入 `take()` 改变“已满”条件；`wait()` 则把暂停与释放同一对象锁组合起来，并由真实状态变化而不是猜测时长驱动唤醒。

## 3. 为什么 `put` 和 `take` 的等待条件必须使用 `while`，而不是 `if`？请同时考虑多个消费者竞争和虚假唤醒。

当线程被唤醒时，可能存在多个线程竞争一个资源，此时唤醒可能会因为未争抢到锁而需要再次进入等待
还存在线程不满足条件时被唤醒，此时需要循环检查来避免程序存在问题

没抢到锁时只是等待获得锁；获得锁并重新检查后条件仍不满足，再次调用 wait()

> **批改：基本正确，但需要区分“暂时没抢到锁”和“条件再次不满足”。** 被唤醒后没获得锁的线程只是在锁入口阻塞，不会立刻再次调用 `wait()`；它获得锁、从 `wait()` 返回并重新检查条件后，如果元素已被其他消费者取走，才会再次进入等待集。虚假唤醒同样不能证明条件成立，因此两种情况都必须由 `while` 重新检查。

### 修正复核

已正确区分锁竞争和条件等待：未获得锁时先等待锁，获得锁后复查条件，条件仍不满足才再次 `wait()`。同时原答案已考虑虚假唤醒，本题通过。

## 4. 为什么本章使用 `notifyAll()`？同一个缓冲区等待集中可能存在哪两类线程，使用 `notify()` 有什么风险？

等待“非空”的消费者/等待“未满”的生产者

> **批改：识别出两类等待线程，但风险描述还不够准确。** `notifyAll()` 也不保证所有线程都能继续执行；它只让所有等待者重新竞争锁和检查各自条件。`notify()` 的关键风险是只任意选择一个等待者，可能唤醒条件仍不满足的角色，例如释放空间后却唤醒另一个等待“非空”的消费者，让真正等待空间的生产者继续沉睡，造成系统无法推进。

### 修正复核

已正确补充 `notify()` 可能唤醒错误角色，使真正满足条件的线程继续沉睡。本题通过；还应保留边界：`notifyAll()` 只提供重新竞争资格，最终能否继续仍由获得锁后的 `while` 判断。
